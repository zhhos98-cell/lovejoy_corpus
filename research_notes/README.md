## 2. Process provenance and historical snapshots

The following file families are normally historical/process material unless explicitly routed from `CANONICAL_INDEX.md`:

- files containing `batch`, `round`, `sweep`, `delta`, `queue`, `freeze`, or `handoff` in a dated historical sequence;
- old `CANONICAL_INDEX_YYYY-MM-DD.md` snapshots;
- prior repository cleanup/freeze scans;
- draft skeletons and architecture logs superseded by a later writing authority;
- intermediate source searches whose state-bearing conclusions have been merged into a terminal dossier.

Do not delete such a file merely because its status language is obsolete. Delete only when it is genuinely supersession-only, contains no unique evidence/provenance needed in the working tree, and the state-bearing result is already merged; Git history remains the recovery layer.

## 3. Evidence labels

Keep these layers explicit:

- **diplomatic transcription** — visible manuscript wording directly read from the image;
- **source-assisted / external-source collation** — printed/source material used to identify or constrain a manuscript reading;
- **editorial reconstruction / argument summary** — normalized explanation of what a page appears to be doing;
- **historical interpretation** — claims about training, transmission, method, politics, chronology, or later significance.

Never silently upgrade one layer into another. Rejected readings, contradictory evidence, and HOLD states remain part of the evidentiary record.

## 4. Naming rule for new material

For new notes, prefer stable object-first lowercase `snake_case` names with ISO dates (`YYYY-MM-DD`) and an explicit status/function when useful. Preserve archival identifiers such as `MS38_...` when they are the actual object key. Existing cited legacy paths remain stable until a mapped migration is worth the reference cost.
